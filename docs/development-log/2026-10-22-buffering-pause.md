# 2026-10-22 이동 직후 버퍼링 중 정지가 무시되는 문제 (#53)

## 1. 배경 / 문제

- #13 작업(`2026-10-22-section-end-action.md` "확인 중 발견한 문제")에서, 재생 위치를 옮긴 직후(`seekTo` 뒤 약 0.3초 안, 플레이어가 버퍼링 중) 일시정지하면 YouTube가 버퍼링(3)에 머문 채 위치만 멈추고 일시정지(2) 이벤트를 보내지 않는다는 것을 발견했다.
- 어댑터는 기술 설계 문서 "상태 머신"대로 버퍼링을 재생 중으로 보므로 앱은 계속 "재생 중"으로 남는다. 정지 버튼을 다시 눌러도 이벤트가 오지 않고, 상태가 재생 중이라 음성 시작 명령은 무시된다. 사용자는 재생 버튼이나 영상 화면으로 풀어야 했다.
- 재생 버튼 직후 정지(#7), 자동 반복 바퀴 경계(#13, 바퀴마다 이동), 구절 인식 점프(#22) 직후에 모두 생길 수 있다.
- 제약: 다른 세션(#23, #28, #29)이 동시에 진행 중이라 고칠 수 있는 파일은 `src/adapters/playerAdapter/*`, `src/controller/playback.ts`, `src/controller/usePlayback.ts`와 테스트, 이 기록뿐이다. `usePlayback`의 공개 형태는 바꾸지 않는다. 기술 설계 문서는 고치지 않는다.

## 2. 검토한 선택지

### 재현 (구현 전, 앱 내 브라우저, 직접 만든 YT.Player에 iframe 명령, 영상 dQw4w9WgXcQ, 음소거)

당시 페이지 `document.visibilityState`는 `visible`이었다.

- `seekTo(t)` + `playVideo` 뒤 50~150ms에 `pauseVideo`: 이벤트는 버퍼링(3)만 오고, 상태 3·위치 고정이 10초 넘게 이어졌다(영상의 89%를 불러온 뒤에도). **버퍼링은 스스로 끝나지 않았다.**
- 멈춘 상태에서 `pauseVideo` 다시 보내기, `seekTo(현재 위치)`, `seekTo` + `pauseVideo`: 모두 이벤트가 없고 상태 3이 유지됐다.
- 멈춘 상태에서 `playVideo`: 약 270ms 뒤 재생(1), 곧바로 `pauseVideo`하면 약 20ms 뒤 일시정지(2). 그 사이 위치가 약 0.3초 진행했다(소리가 잠깐 난다).
- 버퍼링이 먼저 끝난 경우(캐시, 또는 800ms 뒤 정지)는 3, 1, 2 순서로 정상적으로 일시정지가 왔다.

## 3. 결정 및 이유

- 사용자가 비교를 보고 **후보 1**을 골랐다. 후보 3의 재생→정지 보완은 넣지 않았다(소리 샘, 불필요한 명령. 멈춘 플레이어는 실제로 위치가 고정되고 소리가 나지 않으므로 정지로 알려도 실제와 맞다).
- 규칙: 어댑터가 마지막으로 '재생 중'을 알렸고 마지막으로 받은 YouTube 상태가 "정지 요청에 아직 답하지 않은 상태"일 때 `pause()`를 받으면 0.5초(`PAUSE_STUCK_MS`) 타이머를 건다. 그때도 그 상태면 'stopped'를 알리고 마지막 상태를 정지로 기록한다(같은 상태 중복 알림 방지가 그대로 동작).
  - 그 전에 재생(1)·일시정지(2)·끝남(0)·준비됨(5)이 오면 YouTube가 답한 것으로 보고 타이머를 지운다. 버퍼링(3)이 다시 와도 타이머는 유지한다(정지 요청에 대한 답이 아니므로).
  - `play()`, `load()`, `destroy()`는 타이머를 지운다. 정지 직후 다시 재생했는데 늦게 정지가 알려지는 일을 막는다.
- 0.5초인 이유: 버퍼링이 먼저 끝나는 정상 경우에는 정지 요청 뒤 100ms 안팎에 일시정지가 와서 충분히 넉넉하고, 정지 반응 1초 이내(인수 조건)를 지킨다.
- **구현 중 바꾼 점: 시작 전(-1)도 "답하지 않은 상태"로 본다.** 1단계 보고에서는 버퍼링(3)만 보기로 했지만, 실제 앱에서 확인하다가 처음 재생 순서(-1, 3, -1, 3, 1) 중간이나 자동재생이 막혔을 때 -1, 3, -1에서 멈추는 경우를 봤다. 이때 앱은 3 때문에 재생 중이고, 마지막 원래 상태가 -1이라 버퍼링만 보면 타이머가 걸리지 않아 정지 버튼이 듣지 않았다. 같은 원리(정지 요청에 답이 없음)라 같은 처리에 넣었다. 정지 요청이 없으면 여전히 아무 일도 하지 않는다.
- 정지 버튼·정지 명령(`usePlayback.stop()`)과 구간 끝 자동 정지(`checkSectionEnd`의 `player.pause()`)는 모두 어댑터의 `pause()`를 거치므로 두 경로 모두 이 처리를 탄다. 컨트롤러는 고치지 않았다.

### 기술 설계 문서와 어긋나는 부분

- "상태 머신"의 "로딩 중(버퍼링)은 재생 중으로 봅니다"에 예외가 하나 생겼다: **정지를 요청했는데 0.5초 뒤에도 버퍼링(또는 시작 전)이면 정지로 본다.** 또 "상태의 기준: onStateChange"에도, 이 경우만은 이벤트 없이 어댑터가 정지를 알린다는 예외가 생긴다.
- 문서 수정은 이번 파일 범위 밖이라 하지 않았다. 문서에 반영할 때 위 두 문장을 고치면 된다.

## 5. 검증 결과

- Vitest: 28개 파일, 494개 테스트 통과(어댑터 테스트 61개). 최신 `origin/main`(df4f828, #56·#57·#58 포함)을 merge한 뒤 29개 파일, 534개 테스트 통과
- `npm run lint`, `npm run build` 통과
- **실제 영상 확인(앱 내 브라우저, 수정 후 앱, dQw4w9WgXcQ)**: 앱의 재생·정지 버튼을 페이지 스크립트로 눌렀고, 원래 상태와 위치는 `YT.get(...)`으로 50ms마다 읽었다. 자동재생 차단을 피하려고 플레이어를 음소거했다(첫 시험 제외). 구간 3초, 프리롤 1.5초.
  - 재생 버튼 직후 정지(5회, 재생 뒤 50~300ms): 버퍼링에 멈춘 2회(100ms, 300ms)는 정지 클릭 뒤 약 0.5~0.55초에 앱이 "정지"가 됐고 위치가 고정됐다(128.53초, 188.71초에서 1.5초 이상). 버퍼링이 먼저 끝난 2회는 3, 1, 2로 정상 정지. 1회(50ms)는 앱이 아직 재생 중 이벤트를 받기 전이라 정지가 보내지지 않았다(아래 참고).
  - 자동 반복 바퀴 경계 정지(8회, 위치가 되돌아간 것을 본 뒤 10~150ms): 버퍼링에 멈춘 6회 모두 정지 클릭 뒤 약 0.5~0.55초에 앱이 "정지"가 됐고 위치가 고정됐다. 이 경우에는 앱이 정지가 된 뒤 0.25~0.8초 지나 실제 일시정지(2)가 늦게 왔다(앱 상태는 이미 정지라 다시 알리지 않음). 나머지 2회는 정상 정지.
  - 정지 뒤 재생 버튼: 13회 모두 다시 재생됐다(버퍼링 약 0.25초 뒤 재생(1), 그동안 앱은 재생 중 유지 = 정지 요청 없는 일반 버퍼링은 재생 중).
  - 자동재생이 막혀 -1, 3, -1에 멈춘 경우(음소거 없이 페이지 스크립트로 재생): 앱이 재생 중으로 남아 있다가 정지 클릭 뒤 약 0.5초에 정지가 됐다.

**미확인**

- **화면에 보이는 창에서의 확인**: 위 실제 영상 확인 때 Claude 창이 최소화되어 있어 브라우저 창이 화면에 보이지 않았다(`visibilityState`는 `visible`이었지만 화면 캡처와 실제 클릭이 되지 않았다). 그래서 사람이 누르는 클릭 대신 페이지 스크립트로 버튼을 눌렀고, 소리를 켠 상태도 보지 못했다.
- 음성 시작·정지 명령으로 실제 확인: 마이크 발화로 시험하지 않았다. 명령은 버튼과 같은 `play`·`stop`을 거치고, 정지가 된 뒤에는 상태가 정지라 시작 명령이 통과할 것으로 판단했다(코드로만 판단).
- 구간 끝 자동 정지(`checkSectionEnd`의 `pause()`)가 버퍼링 중에 걸리는 경우: 같은 `pause()`를 거치므로 단위 테스트의 어댑터 동작과 같다고 판단했고, 실제 영상으로는 보지 않았다(구간 끝은 재생 중 위치라 버퍼링 중일 가능성도 낮다).
- 구절 인식 점프 직후 정지: 같은 이동+재생(`playFrom`)이라 같다고 보고 따로 보지 않았다.
- Chrome 정식 브라우저, 다른 브라우저, 모바일 기기

## 6. 남은 작업 / 보류 사항

- 기술 설계 문서 "상태 머신"에 위 예외 반영(문서 범위 밖이라 보류).
- 재생 버튼을 누른 직후 앱이 아직 재생 중 이벤트를 받기 전(약 50ms 안)에는 상태가 정지라 정지 버튼이 비활성이고 정지 명령도 무시된다. 기존 상태 규칙(정지 상태에서는 정지 명령 무시) 그대로의 동작이고 사람이 누르기 어려운 짧은 시간이라 이번에 다루지 않았다.
- 자동재생이 막혀 -1, 3, -1에서 멈추면 정지 요청 전까지는 앱이 재생 중으로 보인다(버퍼링(3)을 재생 중으로 보기 때문). 이번 처리로 정지 버튼으로는 풀리지만, 시작 명령 뒤 자동재생 차단 안내(`useVoice`, 상태가 재생 중이 되면 안 뜸)가 뜨지 않을 수 있다. 실제로 그런지는 확인하지 않았다.
