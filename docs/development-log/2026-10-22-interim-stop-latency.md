# 2026-10-22 정지 즉시 실행 옵션과 반응 시간 측정 (#12)

## 1. 배경 / 문제

- PRD F2-6: 정지 즉시 실행 옵션을 켜면 정지 명령을 중간 인식 결과로, 끄면 최종 결과로 실행하고, 두 방식의 반응 시간을 측정해 기본값을 정한다. 이슈 #12의 인수 조건은 (1) 옵션을 켜면 중간 결과로 정지하고 같은 발화에서는 한 번만 실행, (2) 끄면 최종 결과로만 실행, (3) 인식 결과를 받은 뒤 상태가 바뀔 때까지 걸린 시간(ms)을 기록하고 화면에서 볼 수 있음이다.
- #11(`2026-10-21-voice-control.md`)에서 (1)·(2)는 이미 `judgeResult`에 들어가 있었다. 중간 결과는 `stopOnInterim`이 켜져 있을 때 정지 명령만 판별하고, 명령을 실행한 발화 ID를 기억해 같은 발화의 뒤따르는 결과는 보지 않는다. 다만 #11에서는 `judgeResult` 테스트로만 확인했고, 반응 시간은 측정하지 않았다.
- 같은 시기에 #13 세션이 `usePlayback.ts`·`playback.ts`·`playbackMachine.ts`를, 다른 세션이 다른 파일을 고친다. 이 작업은 `useVoice.ts`, `VoicePanel.tsx`, `VoicePanel.css`, 테스트, 이 기록만 고치기로 범위를 정했다.

## 2. 검토한 선택지

- **측정 끝 시점**
  - 플레이어 이벤트가 `usePlayback`의 상태를 바꾸는 순간(`onPlayerEvent`): 가장 정확하지만 `usePlayback.ts`나 `App.tsx`를 고쳐야 해 범위 밖이다.
  - `useVoice`에서 `playback.state`가 바뀐 렌더 뒤의 효과에서 시각을 재기: `usePlayback`의 공개 형태(`state`)만 쓴다. 상태 변화에 화면 반영(렌더·커밋)까지 더해진 시간이 된다.
- **측정 시작 시점**
  - 명령을 실행한 인식 결과를 받은 시각(이슈의 정의).
  - 같은 발화의 첫 인식 결과를 받은 시각. 중간 결과로 실행하면 줄어드는 시간(최종 결과를 기다리는 시간)은 결과 수신 "이전"에 있어, 수신 시각만 재면 두 방식의 차이가 거의 드러나지 않는다.
- **기록 위치**: `singcue:settings`처럼 저장소에 남기기(`storage.ts`·`types.ts` 변경 필요, 범위 밖)와, 화면을 연 동안 메모리에만 두기.

## 3. 결정 및 이유

- 정지 즉시 실행 판별은 #11의 `judgeResult`를 그대로 쓴다. 이 작업에서 바꾸지 않았고, 같은 발화의 중간·최종 결과를 차례로 넣는 테스트를 더했다.
- 반응 시간은 `useVoice` 안에서 잰다. 명령을 실행할 때 기대 상태(정지 → `stopped`, 시작 → `playing`)와 수신 시각을 기억해 두고, `playback.state`가 바뀐 뒤 효과에서 `performance.now()`와의 차이를 낸다. 범위 제약 때문에 끝 시점은 "상태가 바뀌어 화면에 반영된 뒤"다.
- 두 값을 함께 기록한다. `ms`(이슈 정의: 명령을 실행한 결과 수신 → 상태 변화)와 `sinceFirstResultMs`(같은 발화의 첫 결과 수신 → 상태 변화). 뒤의 값이 중간 결과와 최종 결과의 차이를 보여 주므로 #15에서 기본값을 정할 근거가 된다. 다만 첫 결과 이전(말을 시작해서 첫 결과가 오기까지)은 브라우저가 알려 주지 않아 잴 수 없다.
- 명령 후 3초(`LATENCY_TIMEOUT_MS`, 자동재생 감시 시간과 같음)가 지나서야 상태가 바뀌거나 다른 상태(영상 준비 전 등)가 되면 명령의 반응으로 보지 않고 버린다. 자동재생이 막혀 나중에 재생 버튼을 누른 경우가 반응 시간으로 잡히지 않게 하기 위해서다.
- 기록은 메모리에만 둔다. 판별 기록 항목에 결과 종류(중간/최종)와 반응 시간을 붙이고, 평균용으로 최근 50개(`MAX_LATENCY_RECORDS`)를 따로 남긴다. 저장하려면 `storage.ts`·`types.ts`를 고쳐야 해 이번 범위에서 뺐다.
- 화면: 판별 기록의 실행 항목마다 "중간 결과로 실행 · 반응 Nms · 첫 인식부터 Nms"를 붙이고, 그 아래 "반응 시간" 표에 정지(중간 결과)·정지(최종 결과)·시작별 횟수와 평균을 보인다. 스타일은 `VoicePanel.css`에 두었다.

## 4. 구현 내용

- `src/controller/useVoice.ts`
  - 타입: `ResultSource`, `Latency`, `LatencyRecord`, `PendingLatency`, `LatencySummary`. `VoiceLogEntry`에 `source`, `latency`, `VoiceState`에 `latencies`를 더했다.
  - 순수 함수: `measureLatency(pending, state, now)`(기다림/반응 시간/버림), `summarizeLatencies(records)`(명령·결과 종류별 평균). 리듀서 동작 `latency`(기록 항목에 붙이고 `latencies`에 추가).
  - 훅: 발화별 첫 결과 시각과 측정 대기(`pendingLatencyRef`)를 ref로 두고, `playback.state` 효과에서 측정한다. 실행 기록을 명령 호출 전에 남겨 반응 시간을 붙일 항목이 먼저 있도록 했다.
- `src/ui/VoicePanel.tsx`, `src/ui/VoicePanel.css`: 기록 항목의 반응 시간, "반응 시간" 평균 표
- `src/controller/useVoice.test.ts`: 테스트 9개 추가(같은 발화 순서 2, `measureLatency` 3, `summarizeLatencies` 1, 리듀서 3)

## 5. 검증 결과

**자동 검증**

- `npm test`: 테스트 파일 25개, 테스트 383개 통과(`useVoice.test.ts` 25개)
- `npm run lint`: 오류·경고 없음
- `npm run build`: 통과

**브라우저 확인** (앱 내 브라우저, `vite --port 5198`의 `http://localhost`, 영상 `dQw4w9WgXcQ`, 0:20~0:41 구간 1)

아래 항목은 모두 **실제 마이크·음성이 아니라** 페이지에 가짜 `getUserMedia`(오실레이터 스트림)와 가짜 `SpeechRecognition`(스크립트로 같은 발화 번호의 중간·최종 결과를 넣음)을 넣어 확인했다. 플레이어와 앱 코드는 실제 것이다.

- 옵션 끔(기본값): 재생 중 같은 발화의 중간 결과 "멈춰" → 0.6초 뒤에도 "재생 중". 최종 결과 "멈춰" → "정지". 기록 "정지 · 최종 결과로 실행 · 반응 12ms · 첫 인식부터 613ms"
- 정지 상태 "시작"(최종 결과) → "재생 중". 기록 "시작 · 최종 결과로 실행 · 반응 11ms"
- 설정에서 정지 즉시 실행을 켜고 저장(`stopOnInterim: true` 저장 확인): 같은 발화의 중간 결과 "멈" → "재생 중" 유지(기록 없음), 중간 결과 "멈춰" → "정지". 이어서 같은 발화의 중간 결과 "멈춰"와 최종 결과 "멈춰" → 기록이 더 생기지 않음(한 번만 실행). 기록 "정지 · 중간 결과로 실행 · 반응 8ms · 첫 인식부터 309ms"
- "반응 시간" 표에 정지(중간 결과)·정지(최종 결과)·시작(최종 결과) 각 1회와 평균이 보임
- 콘솔 오류 없음, 375px 폭에서 가로 스크롤 없음(`scrollWidth` 375, 표 오른쪽 359px)

**미확인**

- 실제 마이크와 실제 음성으로 정지 즉시 실행(중간 결과 정지)과 한 번만 실행되는지: 앱 내 브라우저가 마이크를 막아 가짜 인식으로만 확인했다. Chrome 정식 브라우저에서 사람이 직접 확인해야 한다.
- 실제 Web Speech API에서의 반응 시간 값과 중간·최종 결과의 차이: 가짜 인식은 결과를 즉시·임의 간격으로 넣으므로 위 수치(8~12ms, 309·613ms)는 실제 반응 시간이 아니다. PRD의 반응 시간 목표(정지 0.1초, 재생 0.5초 이내)도 확인하지 않았다.
- 측정 끝 시점은 상태 변화가 화면에 반영된 뒤라, 플레이어 이벤트 시각보다 렌더 시간만큼 길게 잡힌다. 차이를 따로 재지 않았다.
- 자동재생이 막힌 뒤 버튼으로 재생한 경우 반응 시간을 버리는 동작: `measureLatency` 테스트로만 확인했다.
- `useVoice` 훅과 `VoicePanel` 화면의 자동 테스트: 화면 테스트 환경이 없어 순수 함수 테스트와 브라우저 확인으로 대신했다.

## 6. 남은 작업 / 보류 사항

- 정지 즉시 실행 기본값(현재 꺼짐)은 실제 Chrome에서 두 방식의 "첫 인식부터" 값을 모아 #15에서 정한다.
- 반응 시간을 저장하거나 내보내려면 `storage.ts`와 `types.ts`(백업 형식 포함)를 고쳐야 한다. 이번 범위에서 뺐다.
- 더 정확하게 재려면 `usePlayback`이 상태를 바꾼 시각을 알려 줘야 한다(#13이 `usePlayback.ts`를 고치는 중이라 이번에 건드리지 않았다).
