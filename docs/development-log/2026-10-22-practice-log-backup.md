# 2026-10-22 연습 기록 내보내기·불러오기와 데이터 삭제 안내 (#29)

## 1. 배경 / 문제

- PRD F5-4는 연습 기록을 JSON으로 내보내고 불러올 수 있어야 하고, 사이트 데이터를 지우면 기록이 사라진다는 안내를 화면에 표시하라고 정한다. 이슈 #29의 인수 조건은 "백업 JSON에 연습 기록이 포함되고, 불러오면 기록이 복원된다"와 "사이트 데이터를 지우면 기록이 사라진다는 안내를 화면에 표시하고 내보내기를 권한다"이다.
- 선행 이슈 #18(JSON 백업, PR #46)과 #27(연습 기록 저장, PR #55)이 모두 main에 병합된 것을 확인했다(작업 시작 시 `origin/main` = 1aad407).
- #18은 백업 형식에 `log`를 미리 넣어 두었지만 당시 연습 기록이 없어 항상 `[]`이 나갔고, #27이 같은 키(`singcue:log`)에 `appendLog`로 기록을 쌓기 시작했다. 그래서 먼저 main에서 인수 조건이 이미 충족됐는지 확인하고, 부족한 부분만 채우기로 했다.
- 제약: 다른 세션들이 `App.tsx`, `SettingsPanel`, `settingsForm.ts`, 재생 관련 파일을 동시에 고치고 있어, 이번 작업에서 고칠 수 있는 파일은 `BackupPanel.tsx`·`.css`, `storage.ts`와 각 테스트, 이 기록 파일로 정했다.

## 2. 검토한 선택지

- **인수 조건이 이미 충족된 경우 할 일**: 코드를 그대로 두고 연습 기록 왕복 테스트와 기록만 추가하기, 또는 불러오기 안내에 기록 수를 보여 주는 등 화면을 손보기. 인수 조건에 없는 화면 변경은 범위를 넓히므로 하지 않았다.

## 3. 결정 및 이유

main에서 인수 조건을 항목별로 확인한 결과 모두 충족돼 있어, 코드는 바꾸지 않고 테스트와 기록만 추가했다.

| 항목 | 판단 | 근거 |
| --- | --- | --- |
| (a) 백업 JSON에 연습 기록이 포함되는지 | 충족 | `src/adapters/storage.ts:193` `exportBackup`이 `readLog(store)`로 `singcue:log`를 읽어 `log`에 넣는다. #27의 `appendLog`(`storage.ts:65`)도 같은 키·같은 읽기 함수(`readLog`, `storage.ts:281`)를 쓰므로 새로 쌓인 기록이 그대로 나간다. #27 기록(`2026-10-22-practice-log.md`) 3절, 기존 테스트 "덧붙인 기록은 JSON 백업 내보내기에 들어간다" |
| (b) 불러오면 기록이 복원되는지 | 충족 | `storage.ts:245-253` `importBackup`이 `singcue:log`를 파일의 `log`로 **덮어쓴다**(합치지 않음, `storage.ts:234-238` 주석). 형식 확인(`parseBackup`, `storage.ts:205-232`, 기록 하나라도 틀리면 `invalid-format`)을 먼저 끝내고 실패하면 아무것도 쓰지 않으며(`storage.ts:240-241`), 쓰는 도중 실패하면 쓴 키를 원래 값으로 되돌린다(`storage.ts:254-256`, `restore`). 화면은 덮어쓰기 규칙을 `src/ui/BackupPanel.tsx:96-99`에 안내한다 |
| (c) 사이트 데이터 삭제 안내와 내보내기 권유 | 충족 | `src/ui/BackupPanel.tsx:75-78` "설정, 구간, 가사 매핑, 연습 기록은 이 브라우저에만 저장되며 … 사이트 데이터를 지우면 모두 사라지니 JSON 파일로 내보내 두세요." 이 패널은 `SettingsPanel.tsx:200`에서 항상 렌더링되고, `SettingsPanel`은 `App.tsx:105`에서 접기 없이 렌더링된다 |

- PRD F5-4(`docs/singcue PRD (기능 명세서).md:90`)의 "내보내고 불러올 수 있다"와 안내 요구는 위 세 항목으로 모두 덮인다.
- 다만 "기록을 쌓음 → 내보냄 → 사이트 데이터 삭제 → 불러옴 → 같은 기록, 그 뒤에 이어 쌓임"을 한 흐름으로 묶어 확인하는 테스트가 없어 추가했다. 기존 #18 왕복 테스트는 `exportBackup` 전체를 비교해 기록도 간접적으로 확인했지만, `loadLog`(#27)로 읽히는지와 불러온 뒤 `appendLog`가 이어 붙는지는 확인하지 않았다.

  - 기존 기록 2건이 있는 저장소에 기록 1건짜리 파일을 불러오면 1건만 남는다(합치지 않고 덮어씀)

## 5. 검증 결과

**자동 검사**

- `npx vitest run src/adapters/storage.test.ts`: 62개 통과(이번에 추가한 3개 포함)
- 전체 `npm test`·`npm run lint`·`npm run build` 결과는 PR 직전 최신 `origin/main` 반영 뒤 다시 돌려 PR 본문에 적는다

**실제 브라우저 확인** (앱 내 브라우저, `npx vite --port 5291`로 띄운 `http://localhost:5291`)

- localStorage를 비우고 `singcue:log`에 가상 기록 2건(`fakeVid_001`, 구간 `s1`·`s2`)을 넣고 새로고침
- "JSON 내보내기" 버튼 클릭 → 안내 "영상 0개의 데이터를 singcue-backup-2026-10-22.json(으)로 내보냈습니다.", 만들어진 Blob의 `log`가 넣은 2건과 같았다: 확인
- localStorage를 모두 지우고 새로고침(사이트 데이터 삭제를 흉내) → `singcue:log`가 없음을 확인 → 내보낸 내용을 파일 입력란에 넣음 → "…불러왔습니다." 안내, `singcue:log`가 내보내기 전 2건과 같았다: 확인
- 손상된 JSON(`{"version":1,`)을 불러오면 "JSON 파일이 아니라 불러오지 못했습니다. 기존 데이터는 그대로입니다." 안내가 뜨고 기록 2건이 그대로였다: 확인
- 백업 패널 화면을 스크린샷으로 봤다. 사이트 데이터 삭제 안내 문구(내보내기 권유 포함)가 "JSON 내보내기"·"JSON 불러오기" 버튼 위에 보였다: 확인
- 확인 뒤 localStorage·sessionStorage를 비웠다

**미확인**

- 실제 파일 다운로드: `<a>.click()`을 가로채 `URL.createObjectURL`에 넘긴 Blob 내용과 `download` 이름만 봤다. 브라우저가 디스크에 파일을 저장하는지는 확인하지 않았다.
- 실제 파일 선택 창: 스크립트로 만든 `File`을 `DataTransfer`로 파일 입력란에 넣고 `change`를 일으켰다. 운영체제 파일 선택 창으로 디스크의 파일을 고르는 흐름은 확인하지 않았다.
- 실제 재생으로 쌓인 기록의 왕복: 기록은 localStorage에 직접 넣었다. 재생으로 기록이 쌓이는 것은 #27에서 확인됐고, 이번에는 같은 키·형식이라 다시 재생하지 않았다.
- 불러오기 도중 저장 공간 부족: 테스트(용량 제한 메모리 저장소, #18의 기존 테스트)로만 확인했다.
- 좁은 화면(375px), 다른 브라우저, 실제 모바일 기기, 화면 낭독기 안내

## 6. 남은 작업 / 보류 사항

- 불러오기 성공 안내는 영상 수만 알려 주고 기록 수는 알려 주지 않는다. 인수 조건에 없어 바꾸지 않았다.
- 불러오기는 기록을 합치지 않고 덮어쓴다(#18 결정). 두 기기의 기록을 합치는 기능은 없다.
- 리포트 화면(#28, 다른 세션에서 진행 중)이 연습 기록을 메모리에 들고 있다면, 백업을 불러온 뒤 화면이 바로 바뀌지 않을 수 있다. `BackupPanel`의 `onImported`가 불러온 `backup.log`를 넘기지만 지금은 `SettingsPanel`이 설정만 받는다. 리포트 화면과 연결할 때 확인이 필요하다.
