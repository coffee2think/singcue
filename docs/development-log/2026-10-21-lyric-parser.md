# 2026-10-21 가사·시간 매핑 파서 lyricParser (#16)

## 1. 배경 / 문제

- 3단계(가사·시간 매핑)에서 사용자는 "분:초 구절" 형식으로 한 줄에 하나씩 구절을 입력하고, 목록 끝에 시간만 적어 "마지막 구절 다음 위치"를 지정한다(PRD F3-1, F3-3). 이 텍스트를 구절 목록(`Line[]`)과 `endT`로 바꾸는 순수 로직이 필요하다.
- 기술 설계 문서는 구절 매칭 1단계에서 "가사 줄은 파싱할 때 한 번만 정규화해 둔다"고 정했다. 정규화는 #8에서 만든 `src/core/normalize.ts`를 commandMatcher와 함께 쓴다.
- 저장된 매핑을 다시 입력창에 보여 주려면 매핑을 같은 형식의 텍스트로 되돌리는 함수도 필요하다.

## 2. 검토한 선택지

- **정규화 결과를 둘 곳**: 공용 `Line` 타입(`types.ts`, 저장 형식)에 필드 추가 vs lyricParser에서 `Line & { norm }`인 `ParsedLine`을 따로 정의.
- **시간만 적은 줄이 구절 사이에 있을 때**: `endT`로 쓰기 vs 구절로 세지 않은 줄로 처리.
- **구절 순서**: 시간순 정렬 vs 입력 순서 유지.
- **초 표기**: 두 자리만(`0:05`) 허용 vs 한 자리(`0:5`)도 허용.

## 3. 결정 및 이유

- `ParsedLine = Line & { norm: string }`을 lyricParser에 두었다. `Line`은 storage가 저장하는 형식이라 바꾸면 #6·#14가 작업 중인 저장·화면 코드와 저장 데이터에 영향이 간다. 정규화 텍스트는 입력에서 다시 만들 수 있는 값이라 저장할 필요가 없다. `ParsedLine`은 `Line`이므로 그대로 저장·직렬화에 넘길 수 있다.
- 시간만 적은 줄은 마지막 구절 **뒤**에 있을 때만 `endT`로 쓴다. PRD가 "목록 끝에"라고 정했기 때문이다. 구절 사이에 있으면 구절도 `endT`도 아닌 줄로 보고 `skipped`에 줄 번호를 남긴다. 끝에 여러 개 있으면 마지막 줄을 쓰고 나머지는 `skipped`에 넣는다. 구절이 하나도 없으면 "마지막 구절"이 없으므로 `endT`는 `null`이다.
- 끝의 시간 줄 뒤에 오는 빈 줄이나 형식에 맞지 않는 줄은 `endT` 판정에 영향을 주지 않는다. 메모 한 줄 때문에 `endT`가 사라지지 않도록 하기 위해서다.
- 구절은 입력 순서대로 둔다. 구절 점프는 "고른 줄의 다음 줄"로 이동하므로 순서는 사용자가 쓴 가사 순서여야 한다. 시간이 거꾸로 적힌 경우의 검증·경고는 화면 작업에서 정한다.
- 형식: `^(\d+):([0-5]?\d(\.\d+)?)\s+(구절)$`. 분은 자릿수 제한 없음, 초는 0~59와 소수점(예시 데이터의 `18.4`), 시간과 구절 사이는 공백이 하나 이상이어야 한다. 줄 앞뒤 공백과 CRLF는 허용한다. `시:분:초`, 음수, 초 60 이상, 시간에 구절을 붙여 쓴 줄은 형식에 맞지 않는다.
- 구절 수는 `lines.length`로 두고, 화면에서 형식 오류를 안내할 수 있도록 세지 않은 줄 번호(`skipped`, 빈 줄 제외)도 돌려준다.
- 기호만 있는 구절(예: `0:12 ~~~`)도 형식에는 맞으므로 구절로 센다. `norm`은 빈 문자열이 된다. 간주처럼 이동 위치로만 쓰는 줄일 수 있어 버리지 않았다. 빈 `norm`을 매칭에서 어떻게 다룰지는 phraseMatcher에서 정한다.
- 직렬화 `serializeLyrics(lines, endT)`는 `분:초 구절` 줄과 끝의 `endT` 줄을 `\n`으로 잇는다. 시간은 `formatTime`으로 초를 두 자리로, 소수점 아래는 밀리초까지 반올림해 끝의 0을 지운다(78.4 → `1:18.4`). 부동소수점 오차(`78.4 - 60`)를 피하려고 밀리초 정수로 계산한다. 구절 안의 줄바꿈은 공백으로 바꿔 다시 파싱해도 줄이 나뉘지 않게 했다.
- `normalize`는 그대로 썼다. 바꿀 필요가 없었다.

## 4. 구현 내용

- `src/core/lyricParser.ts`
  - `parseLyrics(input): { lines: ParsedLine[]; endT: number | null; skipped: number[] }`
  - `serializeLyrics(lines: readonly Line[], endT: number | null): string`
  - `formatTime(seconds): string` (분:초 표시, 화면에서도 쓸 수 있음)
- `src/core/lyricParser.test.ts`: 테스트 21개. 데이터는 `examples/sample-video.json`의 가상 구절과 직접 만든 짧은 문구만 썼다.
- `types.ts`, `normalize.ts`, `src/ui`, `src/controller`, 어댑터는 수정하지 않았다.

## 5. 검증 결과

- `npm test`: 테스트 파일 17개, 테스트 240개 통과(이 중 `lyricParser.test.ts` 21개)
- `npm run lint`: 오류 없음
- `npm run build`: `tsc -b`와 `vite build` 통과
- 이슈 인수 조건별 확인(모두 단위 테스트로 확인)
  - "분:초 구절" 줄을 구절 목록으로 파싱, 형식에 맞지 않는 줄은 세지 않음: 확인
  - 목록 끝 시간만 적은 줄은 `endT`, 구절 수에 세지 않음: 확인(구절 사이·여러 개·구절 없음 경우 포함)
  - 파싱할 때 commandMatcher와 같은 `normalize`로 한 번 정규화: 확인(`norm === normalize(text)`, 원문 유지)
  - 매핑을 텍스트로 직렬화하는 함수: 확인(예시 데이터 왕복, 소수점 시간 왕복)
- 수행하지 않은 검증(미확인)
  - 화면에서 입력·구절 수 표시(F3-1의 "인식된 구절 수가 표시된다"): 화면 작업 범위가 아니라 확인하지 못했다.
  - phraseMatcher가 `norm`을 실제로 쓰는지: phraseMatcher가 아직 없어 확인하지 못했다.

## 6. 남은 작업 / 보류 사항

- 화면(가사 입력)에서 `parseLyrics`의 `lines.length`로 구절 수를, `skipped`로 형식 오류 줄을 안내한다.
- 구절 시간이 입력 순서와 맞지 않을 때(뒤 구절이 앞 구절보다 이른 경우) 경고할지 미정이다.
- 구절이 없고 `endT`만 있는 매핑은 직렬화 후 다시 파싱하면 `endT`가 `null`이 된다(구절이 없으면 `endT`를 쓰지 않는 규칙). 저장 데이터에서 이런 경우가 생기는지는 화면 작업에서 확인한다.
- 반복되는 가사 구절 선택(PRD 미확정)은 phraseMatcher 단계에서 다룬다.
