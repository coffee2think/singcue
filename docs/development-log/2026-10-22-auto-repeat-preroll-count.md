# 2026-10-22 [결정] 자동 반복의 프리롤과 횟수 집계 (#24)

## 1. 배경 / 문제

- PRD 미확정 사항에 "자동 반복의 연습 횟수 집계: 바퀴마다 1회로 셀지, 프리롤을 다시 적용할지"가 남아 있고, 기술 설계 문서의 구간 끝 동작 표도 자동 반복에 대해 "프리롤 적용과 횟수 집계는 미확정"으로 두었다.
- 구간 끝 동작(#13)과 연습 1회 판정(#26)이 이 결정을 기다리고 있어, 구현 전에 정해야 했다.
- main의 현재 구조에서 확인한 제약
  - 재생 위치는 `playSection(player, section, preroll)`이 `prerollStart(start, preroll)`(`max(0, start − preroll)`)로 계산해 이동한 뒤 재생한다. 프리롤은 `usePlayback.play`가 누를 때마다 `singcue:settings`에서 읽는다.
  - 재생 중에 위치를 옮기면 버퍼링이 생길 수 있는데, `playbackReducer`는 버퍼링을 재생 중으로 본다. 설계 문서도 자동 반복은 "재생 중을 유지하고 구간 시작으로 되돌아간다"고 정했다. 따라서 자동 반복 중에는 재생 중 → 정지 전이가 일어나지 않는다.
  - #26 인수 조건과 설계 문서의 "연습 기록 시점"은 재생 중 → 정지 전이 때 기록하도록 되어 있어, 그대로면 자동 반복의 바퀴를 셀 수 없다. 설계 문서의 미확정 설계 사항에는 "`practiceCounter`가 구간 완주 이벤트를 받는 방식 검토"가 적혀 있다.

## 2. 검토한 선택지

### 결정 1. 자동 반복으로 구간 시작에 돌아갈 때 프리롤을 다시 적용할지

- **A1. 매 바퀴 다시 적용**(`prerollStart(start, preroll)`로 이동)
  - 장점: 버튼 재생·음성 시작 명령과 진입 위치가 같다. F2-7("구간 앞부분을 놓치지 않고 들어가고 싶다")의 목적이 바퀴마다 똑같이 해당된다. #13이 기존 `playSection`을 그대로 쓸 수 있다.
  - 단점: 바퀴마다 구간 밖 프리롤 구간(기본 1.5초)을 다시 듣는다.
- **A2. 적용하지 않음**(`start`로 바로 이동)
  - 장점: 반복이 촘촘하고 구간 소리만 듣는다.
  - 단점: 끝에서 시작으로 바로 넘어가 박자를 잡기 어렵다. 진입 위치 규칙이 버튼 재생과 달라 두 가지가 된다.

### 결정 2. 자동 반복의 연습 횟수를 어떻게 셀지

- **B1. 바퀴마다 1회**: 구간 끝에 도달한 바퀴마다 기록하고, 정지 명령 등으로 멈춘 마지막 미완 바퀴는 F5-1의 최소 재생 시간 규칙을 적용한다.
  - 장점: 리포트의 "구간별 연습 횟수"(F5-3)가 실제 반복 횟수와 맞는다. 설계 문서가 검토하던 "구간 완주 이벤트" 방식과 같다.
  - 단점: `practiceCounter`가 재생 중 → 정지 전이 말고 "바퀴 완료" 입력을 하나 더 받아야 하고, #13이 그 이벤트를 내보내야 한다.
- **B2. 반복 전체를 1회**: 재생 중 → 정지 전이 때만 기록한다.
  - 장점: 추가 이벤트가 없어 #26을 현재 인수 조건 그대로 구현할 수 있다.
  - 단점: 10바퀴를 돌아도 1회로 세져, 자동 반복 사용자에게 횟수가 의미를 잃는다. 총 연습 시간만 맞는다.
- **B3. 완주한 바퀴만 세고 미완 바퀴는 버림**
  - 장점: 규칙이 단순하다.
  - 단점: 자동 정지 모드(3초 이상 재생하면 1회)와 규칙이 달라 리포트 숫자를 설명하기 어렵다.

## 3. 결정 및 이유

사용자가 A1과 B1을 선택했다.

- **프리롤: 매 바퀴 다시 적용한다.** 자동 반복으로 구간 시작에 돌아갈 때도 `prerollStart(section.start, preroll)`로 이동한다. 프리롤은 바퀴마다 `singcue:settings`에서 읽어, 반복 중에 바꾼 값이 다음 바퀴부터 반영된다. 진입 위치 규칙을 버튼 재생·음성 시작과 하나로 유지하고, 기존 `playSection`을 그대로 쓸 수 있기 때문이다.
- **횟수: 바퀴마다 1회로 센다.**
  - 구간 끝에 도달해 시작으로 돌아가는 시점마다 그 바퀴를 연습 1회 후보로 본다.
  - 정지 명령·정지 버튼·영상 직접 조작으로 멈춘 마지막 바퀴도 1회 후보로 본다.
  - 모든 바퀴에 F5-1의 최소 재생 시간(기본 3초) 규칙을 똑같이 적용한다. 바퀴의 재생 시간이 최소 재생 시간 이상일 때만 기록한다.
  - `PracticeRecord.seconds`는 그 바퀴에서 실제로 재생한 시간이다. 프리롤 구간도 실제로 재생한 시간이므로 포함한다(자동 정지 모드에서 프리롤 위치부터 재생한 시간을 세는 것과 같은 기준).
  - 리포트의 횟수가 사용자가 실제로 반복한 횟수와 맞아야 F5-3의 의미가 산다고 판단했다. 추가 이벤트가 필요한 비용은 설계 문서가 이미 예상한 범위다.

## 4. 구현 내용

이 이슈는 결정만 다루며 코드는 바꾸지 않았다. 결정은 다음 이슈에 반영한다(각 이슈에 결정 내용을 댓글로 남겼다).

- **#13 구간 끝 동작**
  - 자동 반복에서 구간 끝에 도달하면 `playSection`과 같은 방식으로 `prerollStart(section.start, preroll)`로 이동해 재생 중을 유지한다. 프리롤은 바퀴마다 설정에서 읽는다.
  - 구간 끝에 도달해 시작으로 돌아갈 때마다 "바퀴 완료" 이벤트를 `practiceCounter`가 받을 수 있는 형태로 내보낸다. 이벤트에는 바퀴 시작 시각(또는 재생 시간)을 계산할 수 있는 정보가 있어야 한다.
  - #13 인수 조건의 "임시 동작 명시"는 이 결정으로 대체된다.
- **#26 practiceCounter**
  - 재생 중 → 정지 전이 외에 "바퀴 완료" 입력을 받는다.
  - 바퀴 완료 시 그 바퀴의 재생 시간이 최소 재생 시간 이상이면 `PracticeRecord`를 만들고, 다음 바퀴의 시작 시각을 그 시점으로 다시 잡는다.
  - 자동 반복 중 정지되면 마지막 바퀴(마지막 바퀴 완료 이후 재생한 시간)에 같은 규칙을 적용한다.

## 5. 검증 결과

- 코드 변경이 없는 문서 작업이다. 이 브랜치(최신 main 기준)에서 확인한 결과는 다음과 같다.
  - `npm test`: 테스트 파일 25개, 테스트 374개 통과
  - `npm run build`: 통과
  - lint: `npx eslint src`와 `npx eslint vite.config.ts`는 오류 없음. `npm run lint`(`eslint .`)는 이 체크아웃 안의 `.claude/worktrees/`(다른 작업 세션의 worktree)까지 검사하면서 파일마다 1건씩 오류가 나 실패했다. worktree가 없는 체크아웃이나 CI에서는 재현되지 않을 것으로 보지만 확인하지 않았다(미확인). `eslint.config`의 `ignores`에 `.claude`를 넣을지는 이 이슈 범위 밖이라 고치지 않았다.
- 결정의 근거는 PRD(F2-7, F2-8, F5-1, F5-3, 미확정 사항), 기술 설계 문서(상태 머신, 구간 끝 동작 표, 연습 기록 시점, 미확정 설계 사항), main의 `src/core/playbackMachine.ts`, `src/controller/playback.ts`, `src/controller/usePlayback.ts`에서 확인했다.
- 미확인
  - 재생 중 `seekTo`로 구간 시작에 돌아갈 때 실제 YouTube 플레이어가 버퍼링만 내보내고 정지(paused) 이벤트를 내보내지 않는지는 실제 영상으로 확인하지 않았다. 정지 이벤트가 끼어들면 자동 반복 중에도 재생 중 → 정지 전이가 생겨 바퀴가 이중으로 기록될 수 있으므로, #13에서 실제 영상으로 확인해야 한다.

## 6. 남은 작업 / 보류 사항

- #13에서 자동 반복 이동과 "바퀴 완료" 이벤트를 구현하고, 위 미확인 항목(반복 이동 시 플레이어 이벤트)을 실제 영상으로 확인한다.
- #26에서 "바퀴 완료" 입력을 포함해 연습 1회 판정을 구현한다.
- 기술 설계 문서의 구간 끝 동작 표("프리롤 적용과 횟수 집계는 미확정")와 미확정 설계 사항 표, PRD 미확정 사항 표는 이번에 고치지 않았다. 문서를 이 결정에 맞게 갱신할지는 따로 정한다.
- #11 개발 기록에 남은 "자동 반복과 자동재생 차단 감시가 겹치지 않는지" 점검은 #13에서 함께 본다.
