# 2026-10-21 영상 불러오기 화면 (#5)

## 1. 배경 / 문제

- PRD F1-1: 영상 주소(watch, youtu.be, shorts, embed)나 영상 ID를 입력하면 공식 임베드 플레이어에 영상이 준비되고, 잘못된 입력은 오류로 안내하며, 임베드가 막힌 영상은 플레이어 오류 코드를 안내하고 앱이 멈추지 않아야 한다.
- 주소 해석, IFrame 플레이어 래핑, 오류 코드별 안내 문구는 playerAdapter(#3)에 이미 있다. 이번 작업은 `src/ui`에 입력란과 플레이어 영역을 만들어 어댑터를 화면에 연결하는 것이다.
- 컨트롤러(`usePlayback`, 재생 상태 머신 연결)는 이후 이슈 범위라 이번에는 다루지 않는다.

## 2. 검토한 선택지

- **영상을 바꿀 때 플레이어 처리**
  - 플레이어 하나를 유지하고 `PlayerAdapter.load()`(cueVideoById)로 바꾸기: iframe을 다시 만들지 않아 빠르다. 그러나 어댑터는 같은 상태가 이어지면 상태 변경을 한 번만 알리므로, 정지 상태에서 다른 영상을 준비하면 준비됐다는 신호('stopped')가 오지 않는다. 화면에서 "불러오는 중"을 끝낼 기준이 없어진다. 또 StrictMode에서 효과가 두 번 실행될 때 만들고 있는 플레이어를 함께 다뤄야 해 코드가 복잡해진다.
  - 요청마다 플레이어를 새로 만들기: 영상을 바꿀 때 iframe을 다시 만든다. 대신 매번 'ready' 신호로 준비를 판단할 수 있고, 오류가 난 플레이어도 다음 요청에서 깨끗이 바뀐다.
- **화면 상태 관리**: 컴포넌트 안의 여러 `useState`와, 순수 함수 reducer(`useReducer`). 기술 설계 문서가 화면 테스트를 범위에서 제외했으므로 상태 전이를 Vitest로 검증하려면 reducer가 맞다.

## 3. 결정 및 이유

- 요청마다 플레이어를 새로 만든다. 지금 단계에서는 영상을 자주 바꾸지 않고, 준비 판단이 확실한 쪽을 택했다. playerAdapter는 수정하지 않았다.
- 불러오기 요청마다 `requestId`를 붙이고, 앞선 요청의 플레이어가 늦게 보낸 이벤트는 버린다. 같은 영상을 다시 불러와도 새 요청으로 보아 오류 뒤 재시도가 된다.
- 오류는 언제 와도 받고, 오류 뒤에 늦게 온 준비·상태 변경은 오류 안내를 지우지 않는다. 'ready'와 'error'가 오는 순서를 문서에서 보장하지 않으므로 어느 순서로 와도 오류가 남게 했다.
- 입력 오류(빈 입력, 해석 불가)는 입력란 아래에 따로 보여 주고, 이미 불러온 영상은 그대로 둔다. 플레이어 오류는 "플레이어 오류 코드 N: 안내 문구" 형식으로 보여 준다. IFrame API 스크립트를 못 불러오는 경우처럼 코드가 없는 오류는 문구만 보여 준다.
- 상태 안내는 플레이어 위에 둔다. 처음에는 플레이어 아래에 두었는데, 브라우저에서 확인해 보니 플레이어가 화면을 채워 오류 안내가 보이지 않았다.

## 4. 구현 내용

`src/ui/`

- `videoInput.ts`: `readVideoInput(input)`. `parseVideoId`로 해석하고, 빈 입력과 해석 불가에 각각 안내 문구를 돌려준다.
- `videoLoadState.ts`: `videoLoadReducer`. 상태는 empty → loading → ready / error. 동작은 request, playerEvent(어댑터 `PlayerEvent` 그대로), failed(플레이어 생성 실패).
- `VideoInputForm.tsx`: 입력란과 "불러오기" 버튼. 입력 오류는 `role="alert"`로 알린다.
- `PlayerView.tsx`: React가 그리지 않는 요소를 직접 붙여 `createPlayer`에 넘긴다(IFrame API가 요소를 iframe으로 바꾸기 때문). 요청이 바뀌거나 화면에서 빠지면 이벤트를 끊고 요소를 지우며, 준비된 뒤 `destroy()`한다.
- `App.tsx`: 입력란, 상태 안내, 16:9 플레이어 영역을 배치. `app.css`에 최소 스타일.

**자동 검증**

- `npm test`: 테스트 파일 9개, 테스트 129개 통과(이번에 추가한 `videoInput.test.ts` 12개, `videoLoadState.test.ts` 10개)
- `npm run lint`: 오류 없음
- `npm run build`: 통과
- 컴포넌트(`PlayerView`, `VideoInputForm`, `App`)는 자동 테스트가 없다. 화면 테스트는 기술 설계 문서에서 범위 밖으로 정했고, 아래 브라우저 확인으로 대신했다.

**실제 브라우저 확인** (앱 내 브라우저, Chromium 계열, `npm run dev`로 띄운 `http://localhost`)

- 빈 입력 → "YouTube 링크나 영상 ID를 입력하세요." 안내
- `https://example.com/watch?v=...`, `not a video` → 해석 불가 안내. 영상을 불러온 뒤 잘못 입력해도 기존 영상과 "준비됐습니다" 안내가 그대로 남는다.
- watch(`&t=10s` 포함), youtu.be(`?si=` 포함), 스킴 없는 shorts, embed 주소, 11자 ID → 모두 "영상이 준비됐습니다(ID)"가 뜨고 iframe 주소가 `youtube.com/embed/<ID>`. 플레이어 iframe은 항상 1개(StrictMode에서 먼저 만든 것과 이전 영상의 플레이어가 지워짐)
- 없는 영상 ID `aaaaaaaaaaa` → "플레이어 오류 코드 150: 이 영상은 다른 사이트에서 재생할 수 없습니다…" 안내. 콘솔 오류 없음
- 오류 뒤 정상 주소를 다시 불러오면 플레이어가 바뀌고 "준비됐습니다"로 돌아온다(앱이 멈추지 않음).
- 375px 폭에서 가로 스크롤 없음(플레이어 343px)

**미확인**

- 실제로 퍼가기가 막힌 영상(소유자가 임베드를 끈 영상)의 오류 코드 101/150 안내: 그런 영상 ID를 찾지 못해 없는 영상 ID(150)로만 확인했다.
- 오류 코드 2, 5, 100, 153 안내 화면: reducer 테스트(101)와 어댑터의 문구 테스트로만 확인했다.
- IFrame API 스크립트를 불러오지 못한 경우(오프라인 등)의 화면 안내: reducer의 failed 동작 테스트로만 확인했다.
- Chrome 정식 브라우저, 다른 브라우저, 실제 모바일 기기

## 6. 남은 작업 / 보류 사항

- 컨트롤러(`usePlayback`)가 생기면 플레이어 생성과 `PlayerEvent` 처리를 컨트롤러로 옮기고, 'ready'·'stateChange'를 playbackMachine 전이에 연결해야 한다. 그때 영상을 바꿀 때 `load()`를 쓸지 다시 정한다(같은 상태 알림을 한 번만 보내는 어댑터 동작 때문에 준비 신호를 따로 정해야 한다).
- 불러온 영상 ID를 storage에 저장하거나 영상별 데이터를 불러오는 일은 구간 마킹 이슈에서 다룬다.
