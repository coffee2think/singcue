# 2026-10-22 구절 매칭 matchPhrase() (#21)

## 1. 배경 / 문제

- 4단계 구절 인식 점프(PRD F4-1~F4-4)는 사용자가 말한 구절과 입력한 가사 줄의 유사도를 계산해 가장 비슷한 줄을 고르고, 기준 이상이면 다음 줄로 이동한다. 기술 설계 문서는 이 로직을 순수 함수 `matchPhrase`로 `phraseMatcher`에 두고 PoC와 같은 방식을 쓰도록 정했다.
- 선행 작업인 lyricParser(#16, PR #40)와 반복 구절 선택 결정(#20, PR #48)이 main에 병합된 것을 확인하고 시작했다. #20에서 `matchPhrase`에 선택 인자 `hint`(최근 재생 위치)를 추가하고, 최고 점수와 정확히 같은 줄이 여럿일 때의 선택 규칙을 정했다.
- 화면 연결(음성 제어에서 구절 결과로 점프)은 이 이슈 범위가 아니다.

## 2. 검토한 선택지

- **`seekTo`에 프리롤을 뺄지**: 설계 문서 "구절 매칭 설계" 4단계는 "다음 줄 시작 시간에서 프리롤을 빼고 재생"이라고 적었지만, 같은 절의 `MatchResult` 주석은 `seekTo`를 "이동할 시간(초)"으로, 시그니처에는 프리롤 인자가 없다.
  - `matchPhrase` 안에서 빼기: 시그니처에 프리롤 인자가 추가되고, 0초 미만 보정(F2-7)을 중복 구현하게 된다.
  - 다음 줄 시작 시간을 그대로 돌려주고 호출 측이 빼기: 시그니처가 설계와 같다. 버튼 재생은 이미 컨트롤러(`playSection`)가 `prerollStart`로 프리롤을 적용하고 있다.
- **비교할 후보나 줄이 없을 때의 결과**: `MatchResult`를 `null`로 돌려주기 vs `lineIndex: -1`, `passed: false`인 결과로 돌려주기.
- **기준 미달일 때 `seekTo`**: 다음 위치를 그대로 채우기 vs `null`.
- **가사 줄 입력 타입**: `ParsedLine[]`만 받기 vs `Line[]`도 받고 `norm`이 있으면 쓰기.

## 3. 결정 및 이유

- **`seekTo`는 프리롤을 빼지 않은 이동 위치다.** 설계 문서의 `MatchResult` 정의("이동할 시간")와 시그니처(프리롤 인자 없음)를 따랐다. 4단계의 "프리롤을 빼고 재생"은 매칭부터 재생까지의 전체 흐름 설명으로 보고, 실제 적용은 버튼 재생과 같이 호출 측이 `prerollStart(seekTo, settings.preroll)`로 한다. 그러면 0초 미만 보정(F2-7)이 한 곳(`prerollStart`)에만 있다. 테스트로 이 동작을 고정했다.
- **유사도**: 설계 그대로 `1 − 편집 거리 / 더 긴 길이`, 줄 전체 비교와 "들은 말의 길이만큼 줄 앞부분" 비교 중 큰 값이다. 들은 말이 줄보다 길면 앞부분이 줄 전체라 두 값이 같다. 한쪽이 빈 문자열이면 0으로 정했다(0/0을 피하고, 기호만 있는 줄이 골라지지 않게). 편집 거리는 UTF-16 코드 단위(한글은 음절 단위)로 센다. 자모 단위 비교는 설계대로 최적화 단계로 미뤘다.
- **후보**: commandMatcher의 `MAX_CANDIDATES`(5)를 재사용해 앞에서부터 5개만 본다. 후보는 원문을 받아 `normalize`로 정규화하고 빈 후보는 버린다(commandMatcher가 원문을 넘기도록 정한 것과 맞춤).
- **줄 선택**: 줄마다 모든 후보 중 최고 점수를 구하고, 전체 최고 점수와 정확히 같은 줄을 모아 #20 규칙으로 하나를 고른다. (1) `t <= hint`인 줄 중 `t`가 가장 큰 줄(`t`도 같으면 앞 줄), (2) 없으면 `|t − hint|`가 가장 작은 줄(같으면 앞 줄), (3) `hint`가 `null`·생략이면 첫 번째 줄. `NaN` 같은 유한하지 않은 `hint`도 없는 것으로 본다.
- **통과와 이동**: `passed = score >= threshold`. 통과하면 다음 줄 시작 시간, 마지막 줄이면 `endT`(없으면 `null`). 기준 미달이면 이동하지 않으므로 `seekTo`는 `null`로 했다. 화면은 `lineIndex`와 `score`로 가장 가까운 구절과 점수를 보여 줄 수 있다(F4-2).
- **빈 입력**: 비교할 후보나 줄이 없으면 `{ lineIndex: -1, score: 0, passed: false, seekTo: null }`. 설계의 `MatchResult` 형태를 바꾸지 않으려고 `null` 대신 이 값을 골랐다. `threshold`가 0이어도 통과하지 않는다.
- **입력 타입**: `Line | ParsedLine`을 받아 `norm`이 있으면 쓰고, 없으면 `text`를 정규화한다. 설계 시그니처가 `Line[]`이고, lyricParser가 만든 `norm`을 재사용해야 하기 때문이다.
- `MatchResult`는 `src/types.ts`가 아니라 `phraseMatcher.ts` 안에 정의했다(작업 범위가 새 파일로 한정됨).

## 5. 검증 결과

인수 조건별로 확인한 결과다.

- 유사도 `1 − 거리 / 더 긴 길이`, 전체·앞부분 중 큰 값: `levenshtein`, `similarity`, `phraseSimilarity` 단위 테스트와 "줄의 앞부분만 말해도 그 줄을 고른다" 테스트로 확인(성공)
- 후보 최대 5개 × 모든 줄 비교로 최고 점수 줄 선택: 여러 후보 중 둘째·셋째 후보가 이기는 경우와 6번째 후보를 무시하는 경우를 테스트로 확인(성공)
- `passed = score >= threshold`, 통과 시 다음 줄·마지막 줄이면 `endT`·없으면 `seekTo: null`: 경계값(점수 = 기준), 기준 미달, 마지막 줄+`endT`, 마지막 줄+`endT` 없음을 테스트로 확인(성공)
- 반복 구절(#20): 가상 후렴으로 (1) hint 이하 중 가장 늦은 줄(hint가 시작 시간과 같은 경우 포함), (2) hint 이하가 없을 때 가장 가까운 줄과 차이가 같을 때 앞 줄, (3) hint 없음(생략·`null`)을 각각 테스트했다. 점수가 하나뿐이면 hint를 보지 않는 것, 한 글자 다른 변형 후렴은 같은 점수로 보지 않는 것도 확인(성공)
- PoC 점수 분포 재현: 가상의 구절과 가상의 오인식으로 정확 인식 4건(1.00~0.89), 어려운 구절 7건(0.62~0.85)을 만들고 모두 올바른 줄을 고르며 기준 0.5에서 통과하는 것, 관계없는 말 2건(0.38~0.39)은 통과하지 않는 것을 확인(성공). 실제 PoC 로그의 인식 문장이 아니라 직접 만든 값이다.
- `npm test`: 테스트 파일 26개, 테스트 410개 통과
- `npm run lint`: 오류 없음(이 worktree 안에서 실행)
- `npm run build`: 통과
- **미확인**
  - F4-1의 "말하듯 읽었을 때 10번 중 8번 이상 올바른 다음 구절로 이동"(초기 합격선)은 실제 음성 인식과 화면 연결이 필요해 확인하지 못했다.
  - 실제 곡에서 #20 규칙이 기대와 맞는지(후렴을 여러 번 부른 뒤 멈추고 말했을 때)는 화면 연결 후 확인해야 한다.
  - F4-4의 "바꾼 기준이 다음 인식부터 적용"은 `threshold`를 인자로 받는 것까지만 확인했다. 설정 연결은 화면 연결 이슈에서 확인한다.

## 6. 남은 작업 / 보류 사항

- 음성 제어에서 `decide`의 `phrase` 결과를 `matchPhrase`에 넘기고, 플레이어 현재 위치를 `hint`로, `seekTo`에 `prerollStart`를 적용해 재생하는 연결(구절 인식 점프 화면 연결 이슈)
- 기술 설계 문서의 `matchPhrase` 시그니처(`hint` 추가)와 "프리롤을 빼고 재생" 문구가 이번 결정(`seekTo`는 프리롤 적용 전 위치)과 어긋나 보일 수 있다. 문서 갱신은 이번 범위 밖이라 하지 않았다.
- `MatchResult`를 다른 계층에서 함께 쓰게 되면 `src/types.ts`로 옮길지 검토한다.
- 자모 단위 유사도는 최적화 단계로 미룬다.
